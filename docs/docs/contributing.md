# Contributing

Develop changes through reviewed designs and the bundled CAFleet workflows, running repository tasks through their full mise monorepo paths. [SPEC.md](https://github.com/himkt/cafleet/blob/main/SPEC.md) is the specification for the CLI, runtime and storage contracts.

## Project structure

| Entry | Responsibility |
|---|---|
| `go.mod` | The Go module `github.com/himkt/cafleet` and its dependencies; its `ignore ./docs` directive keeps the documentation site out of every `./...` pattern |
| `cmd/cafleet/` | The `cafleet` binary's entry point, which calls the CLI with the embedded assets |
| `internal/core/` | The CLI, the synchronous SQLite broker, multiplexer/process adapters, the member runner and the SQL schema, the `schemaSQL` constant in `internal/core/db.go`, as one package |
| `internal/vt/` | The in-repo terminal emulator: the screen model, its escape-sequence parser and Unicode width tables. Each package's `license.go` carries the upstream copyright and license text of the code it is transliterated from |
| `assets.go` | Embeds the `assets/` tree into the binary |
| `assets/` | Data files: `assets/skills/` installed agent-facing skills, roles and references; `assets/presets/` backend permission/configuration assets; `assets/extensions/` one directory per backend whose plugin or extension `cafleet setup` installs, for Director goals and, where the backend has no native per-tool approval, the Director question tool and the member gate; `assets/profiles/` one runner-profile file per backend with its native screen fixtures. The binary embeds every file |
| `docs/` | Independent operator documentation and its Node/pnpm site tooling |
| `design-docs/` | Numbered design documents and local evidence |

## Go boundaries

Broker queries return typed records; CLI presenters construct wire output. Shared diagnosis validates database identity and schema. Keep durable storage separate from synchronous notification, runner-owned preview retries, input ownership and multiplexer I/O. Required state fails at its read boundary. Preserve process pipe draining, owned-child cleanup, pane ownership compensation and layout cleanup.

Every Go test lives in the `_test.go` file beside the implementation file whose behavior it asserts, in the same package, with its inputs written as literals or generated bytes in that source. Related cases form one table-driven test over a named case slice; runner tests take time from the injected clock and use real time only when they drive real processes, PTYs, sockets or locks; and runner behavior is driven through the runtime scenario harness, which asserts events, rows and child bytes. [Test placement](https://github.com/himkt/cafleet/blob/main/.claude/rules/code-quality.md#test-placement) owns the convention.

## Development

```bash
git clone https://github.com/himkt/cafleet.git
```

Enter the checkout, then install the CLI through its root task:

```bash
mise //:install
```

```bash
cafleet setup
```

`mise //:install` installs `cafleet` into `$GOBIN`, by default `~/go/bin`, which must be on `PATH`. Re-run `cafleet setup` after every install, so the opencode and pi extensions' executable record names the installed binary.

Use `mise tasks --all` as the task registry. The root `mise.toml` pins tools, owns the Go tasks and selects the documentation site's task file through `monorepo.config_roots`. Run Go validation with `mise //:test` and `mise //:lint`; `mise //:coverage` reports statement coverage of the tests. `mise //:test` runs the race detector, which needs cgo on Linux, so a Linux checkout also needs a system C compiler such as gcc; on macOS it needs none. CI runs `mise //:lint` and `mise //:test` on Linux and macOS; its lint job also runs `mise //:vulncheck`, and its Linux test job also runs `mise //:test-shipped`, the cgo-free shipped build configuration. The release build is a cgo-free `go build` with the embedded skills, presets, extensions and profiles. Reinstall the binary after Go changes to use them.

### Installing the skills from your checkout

Setup installs the assets embedded at binary build time; run `mise //:skill-install` after setup to install your working-tree skills instead. Preserve an active executing team's installed assets until its workflow finishes.

## Building docs locally

The documentation site retains its Node/pnpm toolchain and lockfile. Run `mise //docs:install`, then `mise //docs:build`; the build checks links. Use `mise tasks --all` for preview and other available documentation operations. Update dependencies through the manifest and regenerate its pnpm lockfile deliberately.

Follow the [design document workflow](concepts/overview.md#prompts). Preserve role boundaries, clarification, review and user approval. The active session's host rules determine Git and artifact handling.

## Documentation style

State intended behavior directly and describe growing groups through their selecting property or registry; [documentation maintenance](https://github.com/himkt/cafleet/blob/main/.claude/rules/documentation-maintenance.md) owns audiences, shared enumerations, tables and literal formatting.

## Extend a coding-agent backend

Implement a typed permission adapter as the single source of truth for launch-policy choices/default, literal argv mapping and the backend's detector/composer/answer profile. Each backend has one bundled profile, used for every native version; extend it in place when an observed native change requires different rules or plans. [Bundled profiles](https://github.com/himkt/cafleet/blob/main/SPEC.md#bundled-profiles-and-native-screen-fixtures) owns the profile shape, capability independence and coverage. Preserve omitted defaults, native/managed restrictions and sandbox boundaries.

These herdr references, pinned to commit `5608de0608918aba2f9d501e7793b984a0ca9cfa`, provide implementation patterns; each CAFleet profile still requires its own native contract and acceptance evidence.

| Pinned reference | Purpose |
|---|---|
| [Backend manifests](https://github.com/herdrdev/herdr/tree/5608de0608918aba2f9d501e7793b984a0ca9cfa/src/detect/manifests) | Backend-specific live-screen/title rules and controls that distinguish current forms from old transcript text. |
| [Manifest evaluator](https://github.com/herdrdev/herdr/blob/5608de0608918aba2f9d501e7793b984a0ca9cfa/src/detect/manifest.rs) | Region extraction, priority and combined matching conditions for adapting rules with explicit conflicts. |
| [Pane processing](https://github.com/herdrdev/herdr/blob/5608de0608918aba2f9d501e7793b984a0ca9cfa/src/pane.rs) | Ordered PTY-byte processing into terminal state and detector observations. |
| [Terminal snapshots](https://github.com/herdrdev/herdr/blob/5608de0608918aba2f9d501e7793b984a0ca9cfa/src/pane/terminal.rs) | Live screen and title evidence without treating scrollback as a current request. |

Map herdr’s broad `blocked` state into CAFleet’s typed interaction classes, returned-result observations and input-eligibility states. Questions, trust and update screens retain their own classes; a permission request needs the live operation and choice/input region together. Conflicting strongest rules produce an unknown interaction and preserve the native surface. CAFleet owns its runner, profiles, classification, persistence and notification; herdr APIs remain diagnostic, not runtime detection dependencies.

Use safe PTY/terminal APIs behind deterministic transport interfaces. cafleet builds without cgo and imports no `unsafe` package, with a single exception: the audited darwin `__pthread_sigmask` call in `internal/core/time_darwin.go`, which carries its safety invariants inline; add no other unsafe code. Every safe start-time interface applies a same-effective-user check that fails for setuid descendants in the owned process group. PTYs are allocated through `creack/pty`, and the terminal screen model is the in-repo emulator in `internal/vt`, transliterated from vt100 0.18.1 and vte 0.15.0, with their notices in each package's `license.go`. Separate terminal transport, classification and event storage, and preserve bounded shutdown independently of SQLite waits.

Evaluate a candidate backend against the role bar before it ships:

1. Open a design doc for the candidate with a `## Role evaluation` section: a `Role | Requirement | Source | Eligible | Evidence` table with Director `goal`, `pane delivery` and `verdict` rows and one Member row, shaped like the [SPEC Role eligibility](https://github.com/himkt/cafleet/blob/main/SPEC.md#role-eligibility) table.
2. Check each role's Eligible-tier requirements in [SPEC §6.7 Role requirements](https://github.com/himkt/cafleet/blob/main/SPEC.md#role-requirements) against an installed native version, recording the version per requirement group: official documentation and installed `--help` / `--version` for host capabilities, CAFleet PTY probes on each registered multiplexer for runtime behavior. Record the Director `goal` source (`native` or `extension`), and establish `pane delivery` with the backend's `director_delivery` profile capability and a passing [Director delivery probe](#run-a-cafleet-director-delivery-probe) on both tmux and herdr.
3. A verdict is `yes` only when every requirement is established, otherwise `no` with "not established" or the observed failure; the Director `verdict` is `yes` only when `goal` and `pane delivery` are both `yes`, otherwise it names the unmet requirements.
4. For a Member-eligible candidate, claim detection and request-bound allow and deny answers for every approval form the default mode renders, and record the profile's layout limits (`W_min`, wrapped or clipped operations, uncaptured geometries); a default mode rendering no approval form needs no request rules. Claim other bundled-support capabilities with the evidence in the table below; an unclaimed optional capability ships as `unknown` coverage.
5. On shipping, copy the rows into the SPEC Role eligibility table, summarize each role as a `Role | Eligible | Basis` row (sources, checked versions and runtime caveats) in the backend's Role eligibility subsection of `assets/skills/cafleet/reference/coding-agents.md`, and ship only the roles marked `yes`.

| Capability | Required native evidence |
|---|---|
| Permission detection | Live captures of each permission form the claimed policies reach. |
| Composer plans | For prompt and native exec each, empty-composer, typed-literal and post-submit captures with separate literal and submit-key stages. |
| Request-bound answers | Allow and deny pre-stage captures and a continuation capture for each decision. Pin single-request semantics, focus/key stages, request-token revalidation and human/output race behavior. |

Every claimed detector/composer/answer capability requires CAFleet-owned positive and adversarial replay fixtures, including redraw, wrapping, fragmented ANSI/UTF-8, alternate screens, competing forms and quoted transcript false positives. Every capture is real native PTY evidence from the installed native version on each registered multiplexer, including concurrent output/input and the observed-state race boundary. A submission plan is measured, not an assumed Enter mapping. [Release acceptance](#release-acceptance) owns the minimum policies, evidence fields and fault cases. A launch-help probe supplies no detector/composer/answer claim; missing minimum native evidence fails feature acceptance.

### Run a CAFleet Director delivery probe

The Director delivery probe establishes `pane delivery` as [SPEC Role requirements](https://github.com/himkt/cafleet/blob/main/SPEC.md#role-requirements) defines it. Run it per backend on tmux and on herdr, with the shipped build installed through `mise //:install`:

1. Create an isolated database in a fresh short absolute directory, such as one from `mktemp -d`, so the member runtime socket path stays within the platform limit; record its location and run `cafleet setup --database-url sqlite:///<probe dir>/director.db`. Pass the same `--database-url` on every `cafleet` command of the probe.
2. In a pane of the multiplexer under test, start the candidate Director session and register it with `cafleet fleet create --name <name> --coding-agent <backend>`, adding the pane ID and server it asks for when it cannot confirm the candidate's pane ([Director pane verification](concepts/members.md#director-pane-verification)).
3. Have the Director spawn one probe member on any Member-eligible backend, with a spawn prompt that carries the `{database_url}` placeholder, sends `ready` and then ends its turn without further broker traffic; its ID is the sender identity. From a separate shell, send each probe message with `cafleet message send --from-member-id <probe-id> --to-member-id <director-id> "<text>"`, recording its ID and timestamp.
4. **Idle.** Send one message to the idle Director. The preview must start a turn without other input, and the Director's poll must return the message.
5. **Busy.** Ask the Director to run a foreground command of at least 60 s, such as `sleep 90`, and send two messages while it runs. The command must not be interrupted, and both previews must be read no later than the end of that turn.
6. **Draft hold.** Type a draft into the Director composer, send one message, wait 10 s, then clear the draft. Nothing may be typed while the draft exists and the draft must stay intact; after clearing, the preview must arrive.
7. **Interaction hold.** Open a native approval dialog with the setup below, send one message, then answer the dialog. Nothing may be typed into the dialog; the preview must arrive after it closes.
8. **Burst.** During a foreground command, send 10 messages. Every preview must be accepted, and polls must return every ID.
9. **Long preview.** Send a body whose preview reaches the profile's `director_delivery.plain_limit` (the 4000-scalar inline limit when it is null) and one above it. The first preview must arrive intact inline, and the second in the pointer form.
10. **Settle race.** Type a key during the settle window of a delivery. The attempt must record `literal_mismatch` in the delivering member's `director_delivery` diagnostic without a submit key; after you clear the composer, the preview must arrive.
11. Record the backend, native version, multiplexer and its version, pane geometry, message IDs and the check date in the design doc's evidence record.

| Backend | Interaction-hold setup |
|---|---|
| claude | Launch the Director with `--permission-mode default`, then ask it to run a Bash command outside its allow rules |
| codex | Launch with `-s read-only -a on-request -c approvals_reviewer="user"`, then ask it to run a command that writes a file |
| opencode | Add a project `opencode.json` with `"permission": {"bash": "ask"}` (`OPENCODE_PERMISSION` has no effect), then ask it to run a shell command |
| hermes | Use a probe Hermes home with `approvals.mode: manual`, then ask it to run a command matching Hermes's dangerous-command patterns, such as recursively deleting a temporary directory |
| pi | Record `—`: pi has no native approval dialog, because the CAFleet pi gate runs only in members |

Record `—` only for a backend with no native approval dialog; a dialog you cannot reproduce fails the step.

A failed step removes that multiplexer from the backend's `director_delivery.multiplexers`, and the whole capability when none remains. The `pane delivery` row then reads `no`, naming the failed step, multiplexer and version, and the verdict row names `pane delivery`; the backend still runs Director delivery on each listed multiplexer, but is not Director-eligible.

## Testing and release acceptance

[SPEC §9 Testing strategy](https://github.com/himkt/cafleet/blob/main/SPEC.md#9-testing-strategy) states the conformance levels; this section covers how the CAFleet test suite and release process check them.

### Bundled catalog provenance checks

The bundled-catalog guard tests in `internal/core/coding_agent_catalog_test.go` check every provenance rule of [SPEC Bundled profiles and native screen fixtures](https://github.com/himkt/cafleet/blob/main/SPEC.md#bundled-profiles-and-native-screen-fixtures) against the embedded profile files, so a build whose bundled profile files fail them does not pass `mise //:test`. The guard validates every screen of every profile file, including screens that no profile capability cites. The production catalog loader skips the contents of each file's `screens` and of every `fixture_ids` value, so only the guard reads them, and screen validation parses capture versions with the version probe's SemVer rule. The guard reports these errors; the provenance errors carry the prefix `invalid native profile: `, and the pattern-syntax error is a bare line:

| Condition | Error |
|---|---|
| A profile file's `schema_version` differs from `1` | `unsupported profile schema` |
| A profile file's `backend` differs from its file name or test-catalog key | `profile file backend differs from its file` |
| A fixture id is a screen key in two profile files | `duplicate fixture id <ID>` |
| An object in a profile file's text repeats a key, a screen id written twice included | `duplicate object key <KEY>` |
| A `fixture_ids` value names no screen of its own profile file | `<BACKEND> cites unknown fixture <ID>` |
| A `fixture_ids` value is empty | `capability provenance required` |
| A bundled screen's fields differ from the screen field set | `exact required object fields expected` |
| A pattern-bearing field (a rule matcher, frame guard, region matcher, `prompt_pattern` or any other pattern the catalog decoder compiles) contains a Perl class or boundary (`\s \S \d \D \w \W \b \B`) or an escape outside the [pattern syntax](https://github.com/himkt/cafleet/blob/main/SPEC.md#pattern-syntax) | The backend, rule ID and construct, for example `` claude rule claude-bash-command: `\s` `` |

Test catalogs exercise rule and capability validation with stub screens, and the test loader derives missing composer evidence from each composer plan. The guard requires complete captured screens in the bundled catalog.

### Native screen fixture capture

The capture-to-fixture conversion inserts the converted screen under its fixture id in `screens` of `assets/profiles/<backend>.json`, recording the capture's `native_version` and any `composer_evidence` in the screen. It derives `cell_backgrounds` from the capture grid's per-cell `bg` and `cell_styles` from its per-cell faint and foreground attributes, and fixture replay applies each run's background and style before writing its row text. The terminal-screen parser gives a continuation cell default attributes whenever its leading cell receives a wide character, both on the runtime screen and in replay, so replay writes a run's attributes onto the leading cell and leaves the continuation cell to the parser. [SPEC Bundled profiles and native screen fixtures](https://github.com/himkt/cafleet/blob/main/SPEC.md#bundled-profiles-and-native-screen-fixtures) owns the profile file format.

### Storage deadline mechanisms

A runner SQLite attempt enforces the storage deadlines that SPEC states as outcomes: it replaces the connection's default five-second busy wait with its bounded budget, cancels long-running statements within that deadline and restores the prior handler and connection hooks after the attempt.

### Release acceptance

Acceptance evidence for every declared detector, composer and answer capability consists of synthetic terminal replay and real native PTYs on each registered multiplexer.

The release minimum is a real interactive permission request under Claude's native `default` policy and under Codex's native `on-request` policy with `workspace-write`, each on both tmux and herdr. Acceptance records pin exact installed CLI versions alongside the backend's bundled profile, and their permitted disposable fixtures actually reach the native approval surface. Every minimum case demonstrates blocked-model-independent detection, a committed actionable event/inbox record, Director consumption and a preserved original request. Separate fresh requests cover verified Director-auto allow and deny, user-authorized responses under non-auto/unknown modes, manual original-surface input and a user-executed complete bound command. The records show zero response bytes before required user permission. Missing native availability, unknown coverage or an unobserved required case fails overall feature acceptance; unknown coverage is only the compatibility path for other versions/backends. Other backends' profiles retain their own declared acceptance gates.

Automatic-mode acceptance covers Claude `auto` and Codex `approve-for-me` on both tmux and herdr, with automatic review available for the account and model: the omitted-default launch, an auto-approved fixture, an auto-refused fixture whose refusal the member routes to the Director, and, where the native host shows one, an escalated form answered allow and deny. A later-version case repeats the launch, auto-approved, auto-refused and escalated cases on a native version newer than the profile's captures, recording each UI difference that failed to match. A fixture that does not produce its intended screen is a recorded limit for that backend, not a pass.

Delivery acceptance covers every bundled backend on each registered multiplexer, using isolated native sessions and databases and benign marker commands:

| Case | Required evidence |
|---|---|
| Complete profile reuse | Detection, both composer operations and each available semantic answer resolve the same profile and retain actual run/capture identities |
| Native operation plans | Prompt preview and direct prompt create a native user turn; native exec runs a harmless marker command and exposes its result, with literal-to-submit timing recorded |
| Fallback operation | Missing-plan and no-profile cases show the rule-5 fallback sequence of [SPEC Delivery method and interaction priority](https://github.com/himkt/cafleet/blob/main/SPEC.md#delivery-method-and-interaction-priority) and explicit fallback results |
| Busy composer | A busy composer with an executable plan follows rule 4 (`composer_busy` with zero bytes and profile drain once empty, previews pending) without any Escape; a working member with an empty composer row receives profile delivery |
| Interaction deferral | Permission and question remain open with no Escape/literal bytes; answering on the original native surface yields closure, the queued prompt first and then the pending preview, without another send |
| Adversarial transition | A candidate or superseding interaction appearing during chunks/settles stops the write at its complete prefix, keyboard/pointer input there leaves the write running, and observer/owner loss and partial stages follow the complete-prefix stop outcomes |
| Durable retry | A queued prompt or exec drains by fallback and retains one ID/digest after composer changes and repeated queries; duplicate keys, conflicting digests, lost replies and storage failures avoid duplicate dispatch |
| Deferred failure and liveness | After closure with a busy pane lock and no further output/commands, the runner timer either delivers when the lock frees or publishes not submitted at the deadline; temporary storage/observer failure and terminal-commit recovery preserve FIFO/result visibility |
| Schema and reporting | Fresh-schema initialization, canonical digest validation, referential integrity, sequence preservation, self-send/no-pane output and durable reason/state projection for ordinary and history receipts |

Composer-submit acceptance uses the installed evidence versions on both tmux and herdr for every bundled backend. Each record verifies versions from the capturing server's pane and records commands, screen fixtures and timings:

| Case | Required result |
|---|---|
| Pointer at 0.3 s | Hover, wheel and click during the settle or between literal chunks leave the write running and it submits; permission tokens/stages are revoked |
| Keyboard `x` at 0.3 s | The write continues and the mixed literal is submitted; post-submit verification records the outcome |
| Plain threshold | Codex previews of 1007 and 1037 bytes and Hermes previews of 2027 and 2057 characters submit using measured framing or pointer rendering |
| Positive short writes | Japanese previews of 7987 and 12085 bytes continue chunks and submit within 5 s |
| Ineffective submit key | Post-submit verification ends as `uncertain/submit_unconfirmed`, stage `submitted` |
| FIFO stop | After an uncertain prompt or exec, neither a queued exec nor a sweep preview writes a byte until `input reconcile` settles it, on runs with and without composer verification |
| Hermes deletion | Drafts of 2057 characters and 8192 scalars clear and work settlement completes; the larger draft clears within 10 s |

Unit coverage replays each unsubmitted-literal fixture through post-submit verification and obtains `submit_unconfirmed`, and exercises interaction stops, close-stage failures, schema constraints and projection/recovery actions. Measurements establish submitted native input separately from model consumption, permission decisions and command completion.

Live acceptance records carry the source/installed CAFleet version, native CLI version, native configuration/mode, detector and answer profiles, request identity/token, receipt/stage, multiplexer, terminal size, cwd and metadata evidence. They include a permitted operation, an ordinary command failure after allow, an actual permission refusal, an approval that blocks the model, both supported answer routes and observed continuation. The exercised cases cover stale tokens/epochs/events, same/different operation keys, a second answer for an already answered episode, partial writes/lost replies, redraw, fragmented ANSI/UTF-8, primary/alternate screens, resize, title-only prompts, question/trust/update screens, transcript quotes, identical requests, concurrent human/output/input, slow display, database locks, event-channel pressure, startup compensation, runner hard kill and deletion. Unavailable native modes or unobserved cases remain explicit coverage limits and cannot pass that profile's release gate.

Acceptance also covers these transport, lifecycle and persistence cases:

- Exact child argv for the selected native policy, with native/managed restrictions and sandbox boundaries preserved.
- Equal run IDs across sibling databases, and replacement at an unchanged path.
- A held write transaction and a long statement, showing that restoration and exit are independent of the connection's default timeout.
- A child exiting while its descendant holds the slave, exit during a stalled display and a locked database, and deadline-bounded terminal restoration.
- Timeout followed by the original runner's recovery, and concurrent recovery attempts.
- A command containing a known secret, which is absent from every database/message field.
- Hard kill with uncommitted transitions, loss closure after a committed opening, concurrent recovery, interruption during recovery, and deregistration before recovery with archived rather than fabricated inbox records.
- A live unlinked lock resolved by `member delete`, verified death, unknown identity reporting `live_or_unreachable` and concurrent database-only recovery.
- Cross-invocation accepted-then-failed-stamp recovery, queued-then-drained delivery after interaction closure, disconnected partial writes, receipt retirement followed by a delayed request, and a lost explicit-command stdout result.
- Every registered backend's omitted-policy argv and each adapter-declared explicit policy.
