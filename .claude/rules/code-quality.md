# Code Quality

## No meaningless fallbacks

Do NOT reach for a defaulting accessor when the value is guaranteed to exist. Use direct access and let the code fail loudly if the assumption is wrong.

**Banned patterns:**

| Language | Banned | Use instead |
|----------|--------|-------------|
| Go | `v := m[k]` when the invariant requires `k` to be present | `v, ok := m[k]` followed by `if !ok { panic("<why the invariant holds>") }` |
| Go | `x, _ := f()` discarding an error | Handle the error or return it |
| Go | Returning a default value with a `nil` error when the operation failed | Return the error |
| TypeScript | `value \|\| "Unknown"`, `value ?? "?"` | `value` (trust the type) |

**Exceptions** (where a default IS appropriate):
- A default that is the documented correct behavior for an expected absent value (e.g. an optional config field with a sensible default)
- Data from external/untrusted sources where the schema is not guaranteed

When in doubt, prefer a loud panic or a typed error over a silent wrong value.

## No unnecessary comments

Only add comments where the logic is genuinely non-obvious. Do NOT add:
- Comments that restate the code (`// Create the session`, `// Return the result`)
- Doc comments that restate the test name or type name
- Multi-paragraph explanations of design decisions (put those in design docs)
- Comments explaining what a function's parameters do (use the type signature)

## Test placement

Every Go test lives in the `<file>_test.go` beside the implementation file whose behavior it asserts, in the same package, and `mise //:test` runs it.

- Place each test in the `_test.go` of the file that defines the entry point it asserts on. When a test drives several files, the file that owns the asserted behavior owns the test. Keep related tests together in that file.
- Put a helper or test-only constructor shared by tests of several files into the `_test.go` of the file that owns the type it builds; a helper used only by one file's tests stays in that file's `_test.go`. Every `_test.go` of a package shares its scope, so every test of the package sees these helpers. The `internal/core` test helpers shared by every file, the re-executed child naming and the `-update-golden` flag, live in `internal/core/main_test.go`. Reuse an existing helper or production function (clocks, digests, frame codecs, fixtures) before writing another.
- Write test inputs as literals or generated bytes in `_test.go` source. Every test drives production code and asserts what that code decides or produces. A test reads the data files under `assets/` (the files production code embeds, including the native screen fixtures inside each profile file) through `cafleet.Assets` only as input to that code or as the expected value of its output, such as comparing installed bytes with the embedded bytes, and asserts none of their text, keys, counts, ids or layout.
- A golden test records what production code reports for inputs it does not author: the screens `TerminalState` builds from fixed-seed generated streams, and the observations the detector reports for every bundled native screen fixture (screen hashes, observation kinds, rule ids, regions, operations, choices and composer text). Its expected values sit between `// BEGIN GENERATED: mise //:test -- -run '<TestName>' -update-golden` and `// END GENERATED` lines; the update mode rewrites only that block from the current output, and the regenerated block is reviewed as a behavior diff in the change that alters it. Golden tests are the only tests that record rule ids from the embedded profiles.
- A re-executed child test runs `os.Args[0] -test.run '^<name>$'` with an environment guard and calls `t.Skip` when the guard is unset; derive `<name>` from the function value with the `main_test.go` helper, so renames keep every launcher correct.
- Test-only harness code is itself test code: it lives in the `_test.go` of the implementation file it instruments.
- Write related cases as one table-driven test over a named case slice, naming the case in every assertion message.
- Runner code takes time from the injected `clock`, and its tests use `testClock`; real sleeps and real deadlines belong only to tests that drive real processes, PTYs, sockets or locks.
- Drive runner behavior through the scenario harness in `internal/core/runtime_service_test.go`, asserting events, rows and child bytes.
- Every test and subtest calls `t.Parallel()` unless it changes process-wide state (environment, working directory, umask, signal handlers, rlimits); the `paralleltest` and `tparallel` linters enforce this.

**Forbidden patterns:**
- A test data file or data directory, `testdata/` included.
- A `_test.go` that exercises another file's implementation.
- An external test package (`package <name>_test`); tests are white-box, in the package they assert on.
- A test that asserts the text, keys, counts, ids or layout of an embedded data file instead of the behavior of the code that consumes it.
- A hand-edited line inside a `BEGIN GENERATED` / `END GENERATED` block.

## Database schema

The `schemaSQL` constant in `internal/core/db.go` is the complete schema; edit it in place for every schema change. Each cafleet version uses its own default database file, `cafleet_<VERSION>.db`, so every release starts from a fresh database and no data carries across versions. Schema initialization records the creating version in `cafleet_database`. Setup and the command guard accept only a file whose application identity and recorded version match the running binary, and refuse every other populated file as incompatible without writing to it.
