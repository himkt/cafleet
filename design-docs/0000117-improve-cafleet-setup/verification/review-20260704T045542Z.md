## Nits

### N-1. `cafleet/src/cafleet/cli/_helpers.py:26-33` — two branches raise the identical no-install error

`ensure_skills_current()` raises the same `ClickException("no skills install is recorded; run 'cafleet setup' first")` from two separate branches (table missing; table present but empty). Both branches are correct per Decision 5 ("missing table or empty table = setup never ran → same hard error"); the duplication is purely textual.

**Correct behavior**: state the "setup never ran" condition once, e.g. `if not skill_installs_table_exists() or not (rows := list_skill_installs()):` — a single raise site keeps the two conditions provably identical if the message ever changes. Cosmetic; fine to leave as-is.

### N-2. Guard side effect: a fleet-scoped command on a never-setup machine creates a zero-byte DB file

`skill_installs_table_exists()` opens a session against `settings.database_url`; SQLite's connect creates an empty file when the parent directory exists, so `cafleet fleet list` on a fresh machine leaves a 0-byte `cafleet.db` behind before erroring. This is benign — `run_db_init` treats an empty DB (no tables, no `alembic_version`) as fresh and migrates it normally, so no repair path is broken — and the missing-parent-directory case is correctly reported as "no install" via the documented `OperationalError → False` branch. Recording it here so the behavior is a known, intended consequence rather than a surprise; no change requested.

The diff is a model of the rule, in both directions of the change:

- **Docs prescribe the desired behavior.** The old `install.md` "No migration from an older schema" warning — a reactive prohibition ending in "delete the database" — is replaced by a positive specification ("Upgrading an existing database": migrate in place, data preserved, with the two refusals stated as guarded invariants and the `alembic stamp head` escape hatch named). The Dashboard hint now tells the operator what to do (`create a fresh fleet with cafleet fleet create`) and states the invariant ("schema migrations preserve existing data but never backfill the Administrator") instead of pointing at a removed command.
- **Every prohibition is paired with its affirmative.** Each guard/pre-flight error names its repair command in the same sentence (`run 'cafleet setup' first`, `run 'cafleet setup skill' to reinstall`, `run 'cafleet setup' or 'cafleet setup db' first`); the two `run_db_init` refusals state what the driver will not do and what the operator can do. The cli-options/SPEC guard sections specify the positive procedure as numbered steps with "otherwise proceed silently" as the terminal state.
- **Code fails fast; defaults are documented expected states.** No `.get(key, default)` on guaranteed keys anywhere in the diff — `row["cafleet_version"]`, `ctx.obj["json_output"]`, `os.environ["TMUX_PANE"]`, `json.loads(body)["assets"]` (external input, correctly wrapped in a typed re-raise) are all direct accesses. The single swallowed exception, `OperationalError → False` in `skill_installs_table_exists` (`broker/skill_installs.py:16-20`), is the legitimate-default case under the rule: an unopenable database *is* the expected "setup never ran" state, the docstring says so, and the caller converts it to a loud, actionable error rather than continuing.
- **Tests assert invariants, not absences-of-symptoms** — e.g. `_forbid_network` raises `AssertionError("unexpected network access")` instead of silently stubbing, and the removed-group test asserts the current behavior (Click's own error) per the removal rule.

The two rating deductions are NB-1/NB-2 above — consistency drifts, not affirmative-writing violations.
