The user's request:

Title: Esc-safeguarded `cafleet member nudge` for monitoring-member->Director re-engage.

Problem (with a real incident): The monitoring member re-engages an idle/stalled Director by calling `cafleet message send`, which delivers via `broker.messaging._try_notify_recipient` -> `TmuxMultiplexer.send_inline_preview`. That path calls `_send_literal_then_enter(...)` WITHOUT `esc_first`, so when the Director's pane is parked on a pending permission-approval prompt (e.g. a deny-listed `git push`), the preview's keystrokes confirm the prompt and execute the dangerous command. This actually happened in a live session: the monitoring member correctly diagnosed that the Director was stuck on a `git push` permission prompt and sent a nudge message advising "Cancel it (Esc)" — but the act of DELIVERING that message via the non-Esc-safeguarded inline-preview path pressed Enter on the prompt and executed `git push` (which returned exit 128, no upstream branch). The advice to press Esc was itself what confirmed the prompt.

Aggravating factor: the preview payload in `send_inline_preview` embeds a raw newline between the envelope line `[cafleet msg ...]` and the body (cafleet/src/cafleet/multiplexer/tmux.py around line 246). Under `tmux send-keys -l` a literal newline is itself a submit keypress, so a pending prompt can be confirmed by the envelope line's terminating newline before the explicit trailing Enter — and before the body is even fully typed.

The safeguard placement is currently inverted. `send_wake_trigger` (monitor loop -> monitoring member's own pane) HAS `esc_first=True`, but the monitoring member's pane is never sitting on a permission prompt, so that Esc is unnecessary ceremony. The Director's pane IS routinely on a permission prompt, but the monitor->Director re-engage path has NO Esc safeguard.

Proposed design (from the user):
1. Add a dedicated `cafleet member nudge` subcommand that the monitoring member invokes to re-engage the Director. It carries the message/summary AND leads with an Esc-safeguard (esc_first), isolating the dangerous keystroke behind a purpose-built primitive instead of overloading the general `cafleet message send`.
2. Invert the safeguard: drop `esc_first` from `send_wake_trigger` (monitor->monitoring-member, never on a prompt — just send the trigger plainly); add `esc_first` to the new Director-nudge keystroke path.

Open questions the design doc MUST resolve (do not leave these implicit):
(a) Scope — is `cafleet member nudge` the complete fix, or does the general `cafleet message send` -> `send_inline_preview` path also need an Esc-safeguard (or a pane-state pre-check) for OTHER recipients? A Director->member message landing while that member sits on a deny-list prompt has the identical failure mode. `_try_notify_recipient` does no pane-state check today. Make a recommendation and justify it.
(b) The embedded-newline submit in `send_inline_preview` (the newline between envelope and body) — propose a concrete fix so the explicit trailing Enter is the only submit keypress.
(c) Authorization — the `cafleet member *` subgroup is Director-only today (member create/delete/capture/exec/ping/send-input), but `nudge` would be invoked BY the monitoring member (a non-Director). Define who may call `member nudge` and how that fits the existing fleet-isolation / caller model. Note existing `member ping` is a Director->member fixed-action Esc+poll keystroke; the new `nudge` is monitoring-member->Director carrying a summary, so consider both the keystroke shape and whether it persists a broker task (the Director's facilitation loop ACKs broker messages today).
(d) Esc-during-active-generation tradeoff — the original code comment (tmux.py around line 68-70) claims an Esc before an inline preview would "mis-fire". Validate whether an Esc on an empty prompt / mid-generation is actually harmful versus the catastrophic auto-confirm it prevents, and let that analysis drive the recommendation for (a).
