Fix a confirmed bug in the CAFleet monitor heartbeat. This is design 0000097, slug monitor-wake-names-due-agents. It follows 0000096 (per-member-monitor-intervals), which is Complete.

THE BUG (confirmed by code investigation):
The monitor loop computes the exact set of freshly-due watched agents each tick but discards that information when it wakes the monitoring member. As a result the monitoring member is told, on every wake, to inspect the Director — never the member that actually came due. The user's report: "on every schedule, monitoring target becomes director."

EVIDENCE (read each of these files yourself before drafting):
1. cafleet/src/cafleet/monitor/loop.py :: monitor_tick (around lines 83-112) — it builds the due list correctly over the watched set (root Director at 180s plus ordinary members at 720s). Each due entry is a full target dict carrying agent_id, name, and is_director. But the wake call passes only the WATCHER's coordinates: send_wake_trigger(target_pane_id=watcher pane, fleet_id, agent_id=watcher agent). The due list is used only for broker.record_pings(...) and the per-due-agent stdout echo — it is never communicated to the monitoring member.
2. cafleet/src/cafleet/multiplexer/tmux.py :: send_wake_trigger (around lines 204-238) — it emits a FIXED, Director-centric single-line payload that begins with the bracket tag "[monitor] wake:" and says "capture the Director pane, judge it active vs idle, and if idle assess the inbox and members and re-engage the Director". It names only the Director, gates member-assessment on "if idle", and does not name the due members or instruct re-querying monitor status.
3. cafleet/src/cafleet/multiplexer/base.py :: Multiplexer.send_wake_trigger (around lines 153-174) — the protocol signature is (target_pane_id, fleet_id, agent_id); its docstring has stale drift: it claims "Both ping helpers lead with an Esc safeguard", which is false since design 0000092 section 2 removed the leading Esc from the wake nudge. Fix that stale docstring as part of this change.
4. The intended routine is documented in design-docs/0000096-per-member-monitor-intervals/design-doc.md sections 4 and 6, and in skills/cafleet-agent-team-monitoring/SKILL.md (the canonical spawn prompt steps 1-4 and the quoted wake-nudge text near lines 95-101): re-query monitor status, capture the Director, capture EACH freshly-due member read-only, then re-engage the Director. 0000096 section 4 has the monitoring member RE-DERIVE the due set from "smallest last-ping age", which is ambiguous when multiple agents come due on one tick — the exact inference the loop already performed and threw away.

NET EFFECT: members enrolled at 720s have their cadence stamped by record_pings but are never actually inspected; the effective monitoring target collapses to the Director on every wake.

RECOMMENDED FIX (root-cause, affirmative — but treat as a proposal and confirm the design decisions with the user via clarifying questions):
Thread the freshly-due agents' identities from monitor_tick into send_wake_trigger and embed them in the wake-nudge payload, so the nudge names exactly which agents are due (id plus a role label director/member plus name) and instructs the monitoring member to inspect each due agent's pane read-only PLUS the Director's pane (always — the Director is the only actuation target), judge active/idle and progressing/stalled, and re-engage the Director via "cafleet member nudge" when the Director is idle with un-acked work or any due member looks stalled. This removes the Director-centric framing and the ambiguous re-derivation.
