## Background

The existing `CodingAgent` trait owns names, argument validation, availability checks, and launch argv. The CLI, asset installer, configuration resolvers, and doctor each have backend integration points. SQLite stores backend names as text, so adding the name itself requires no migration; the durable execution scope proposed below does.

Hermes differs from a process-owned CLI session. Its documented classic interface attaches to a gateway-owned session, and closing a client can leave accepted work running. Consequently, killing the CAFleet pane alone cannot satisfy member termination. See [Hermes CLI](https://hermes-agent.nousresearch.com/docs/user-guide/cli) and [Sessions](https://hermes-agent.nousresearch.com/docs/user-guide/sessions).

Evidence gathered during this design task is limited to help output, official documentation, and read-only source inspection. The installed package directory is `0.22.4`; the prior inventory reported `hermes --version` as `vunknown (2026.9.24)`. Those labels are observations, not a supported version floor. No agent/model session, profile mutation, gateway operation, installation, update, or service operation was performed for this design.

The live working tree contains unrelated source changes and deleted documentation. Paths below identify intended integration owners; implementation reconciles them with the repository state at that time and preserves unrelated work. This task produces the design only.

### Owned Runtime Identity

Give each ordinary Hermes member one exclusively owned named profile. Every process launch starts a fresh conversation with the complete requested launch policy. Hermes assigns the conversation's session ID; the profile identifies CAFleet's cancellation boundary for native managed work, including automatic context continuations and persistent background processes. Bind managed processes to the owned session/task and stable PID/start identity, preserving witnesses outside the deletable profile before mutation. Recovery settles that managed work and ownership before deregistration; replacement member creation allocates a new profile and starts a fresh conversation.

The supported termination boundary is Hermes-managed work. An independently daemonized descendant that has left native tracking is outside the complete-discovery guarantee. Report any observed escape, surviving known process, unavailable inventory, ambiguous identity or incomplete control as cleanup uncertainty and retain the member/runtime row and recovery evidence. This boundary supplies no claim of exhaustive operating-system containment. Preserve the admission-fencing, writer-join, durable-operation, lock, incarnation, isolation and retry requirements below within the supported boundary.

Add an additive migration, using the next available refinery version, with this logical schema:

```sql
CREATE TABLE hermes_member_runtimes (
    member_id INTEGER NOT NULL PRIMARY KEY
        REFERENCES members (member_id) ON DELETE RESTRICT,
    hermes_root TEXT NOT NULL,
    profile_name TEXT NOT NULL,
    cleanup_state TEXT NOT NULL
        CHECK (cleanup_state IN (
            'reserved', 'published', 'cleanup_required',
            'cleanup_queued', 'cleanup_dispatch_intent',
            'cleanup_completed', 'cleanup_uncertain', 'settled'
        )),
    cleanup_operation TEXT,
    cleanup_action TEXT
        CHECK (cleanup_action IN ('profile_delete', 'identity_purge')),
    cleanup_result TEXT,
    verified_profile_identity TEXT,
    UNIQUE (hermes_root, profile_name)
);
```

`hermes_root` is a canonical absolute directory. Encode the identity as the UTF-8 JSON array `[canonical_database_path, member_id, registered_at]`, with compact JSON serialization and an integer member ID; use the first 32 lowercase hex characters of its SHA-256 digest as `scope_id`. The profile name is `cafleet-<scope_id>`. The active profile home is `<hermes_root>/profiles/<profile_name>`. Generate each cleanup operation ID from that identity plus the cleanup start timestamp, and retain its action/result until the next explicitly permitted operation replaces it or the runtime row is removed. These states describe CAFleet's lifecycle, not inference activity.

The database row is the durable ownership record. Preparation uses `<hermes_root>/profiles/.cafleet-staging/<scope_id>/`, a hidden directory excluded from Hermes profile enumeration. CAFleet owns this staging namespace; create it with mode `0700`, reject symlinked components, and fail on an existing scope directory at fresh creation. Inside a completed stage, write `.cafleet-owner.json` with `format: 1`, the full database-path digest, member ID, registration timestamp, profile name, and root. The file travels into the active profile in the publication rename. Its exact values must match the row before any existing active profile can be removed.

Persist the `reserved` runtime row in the same transaction as the pending placement, while holding the lifecycle/scope locks below. This row authorizes cleanup of its private hidden stage even if a crash prevented writing the owner marker. Initial verification of an active profile requires the matching marker. Before any destructive dispatch, open the directory without following symlinks, verify its marker, compare descriptor/path identity, and commit `verified_profile_identity` as compact JSON containing `device`, `inode`, `birth_time_ns` and the verified owner-marker SHA-256. Use decimal strings for filesystem identity numbers. The accepted filesystem must expose a stable directory birth identity; an unavailable identity is a compatibility failure, not an omitted check.

That committed identity authorizes reconciliation of the same directory incarnation after recursive deletion removes its marker. Re-open and compare device/inode/birth identity under the scope lock before every continuation; an initially unmarked directory with no recorded verified identity, a changed identity, symlink, or a conflicting remaining marker is an ownership conflict. Preserve that evidence through cleanup failures and remove it only with the runtime row after all profile/stage cleanup settles. The directory's existence alone establishes no ownership, and the verified identity cannot authorize a replacement at the same path.

| Durable row and filesystem state after a crash | Recovery through `cafleet member delete MEMBER_ID` |
|---|---|
| `reserved`; both stage and active profile absent | No Hermes effect occurred; remove the runtime row and deregister |
| `reserved`; hidden stage present, active profile absent | Remove only the recorded private stage, then deregister; the stage was never eligible for gateway adoption |
| Any non-settled state; active profile has matching owner marker | Verify/record its incarnation, then reconcile/cancel it, even if publication happened before the `published` update |
| Partial deletion removed the marker; recorded verified incarnation still matches | Preserve ownership and reconcile the previous operation before continuing that exact partial deletion |
| Active profile has no initial marker/verified identity, a conflicting marker, or a replaced incarnation | Report ownership conflict and retain the row/member; preserve the profile |
| `settled`; both stage and active profile absent | Finish pane/registry settlement without another Hermes deletion |
| Final deregistration/runtime-row removal committed | All profile/stage/marker filesystem cleanup already completed; ordinary repeated deletion reports the existing not-found result |

`member show --json` gains `hermes_runtime: {profile_name, profile_home, cleanup_state, cleanup_operation}` for these members and `null` for other backends. Keep placement JSON unchanged. Human output shows the optional detail only for Hermes. `doctor --json` reports pending/conflicting/uncertain rows and the exact `member delete MEMBER_ID` recovery command, including the explicit database selection when needed. Retain empty staging containers and lock files as stable infrastructure; their deletion is outside member teardown.

### Preparation and Launch

Implement filesystem/process operations in a dedicated `coding_agent/hermes_runtime.rs` module behind an injectable runtime interface. Keep the `Hermes` backend's validation and argv construction pure. Extend launch construction with a backend-neutral context containing the member ID, absolute cwd, and optional prepared runtime scope; existing backends ignore the new scope.

The preparation sequence is:

1. Validate arguments, binary, source-home resolution, installed assets, multiplexer context, provider/auth policy, and source config shape before mutation. Acquire the fleet's shared lifecycle lock.
2. In one short registration transaction, allocate the member and pending placement, derive its scope, acquire that scope's exclusive lock without blocking, and insert the `reserved` row. Commit while retaining both locks. A failed scope-lock acquisition rolls back registration.
3. Create the hidden stage directly with Rust filesystem operations. Write the materialized configuration, selected static secrets, minimal auth metadata, private skills, `.no-bundled-skills`, and `.cafleet-owner.json`; create empty `memories/`, `sessions/`, and `cron/` directories. Flush each file and the stage directory before publication. A partial stage remains invisible to profile enumeration.
4. Revalidate the active member, fleet, pending placement and runtime identity. Rename the completed stage to the previously absent active profile path with same-filesystem, no-replace semantics, then fsync the profiles directory. Use a safe no-replace filesystem API; a plain overwrite-capable rename is insufficient. Record `published` after the rename. A crash between these steps is recovered using the matching marker.
5. Build argv and split the pane with `HERMES_HOME=<recorded-hermes-root>`, the owned `--profile` selector, and broker/multiplexer context. Hermes resolves its process home to the profile. Acquire the resulting pane-input lock while still holding the scope lock, patch the pane ID, commit placement, then release pane, scope and fleet locks. The ready message remains the workflow startup confirmation.

Direct hidden staging intentionally avoids `hermes profile create`: installed `create_profile` publishes before notifying/registering gateway services, which would expose seeded configuration before CAFleet's overrides. A `config.yaml` identity makes the completed directory discoverable; Hermes's existing periodic discovery or explicit chat launch may adopt it only after publication. CAFleet creates no alias/service and invokes no privileged registration. M2/M4 must verify direct staged-profile recognition and its no-bundled-skills marker on the accepted build, with a multiplexer already running. If the installed profile layout needs another identity field, revise this schema before implementation rather than publishing an incomplete profile.

Use the same lock hierarchy across creation, member deletion, and fleet deletion: fleet lifecycle lock first, runtime-scope locks in sorted canonical path order second, then concrete pane-input locks in their existing sorted order. Place lifecycle/runtime locks alongside existing database-adjacent pane locks: `<canonical-db-path>.pane-locks/fleet-<fleet-id>.lifecycle.lock` and `hermes-<scope_id>.runtime.lock`. Use shared lifecycle locks for member create/delete and an exclusive lifecycle lock for fleet delete. Hold the creator's shared lifecycle and exclusive scope locks through publication, pane placement, or full rollback. Message-input operations continue using their pane lock; they acquire no fleet/scope lock, so they cannot invert the hierarchy.

After obtaining locks, re-read the fleet's active state, member state, placement, and runtime identity in a short transaction. A mismatch releases the acquired locks and restarts acquisition against the current snapshot, within its acquisition budget. No SQLite write transaction spans configuration I/O, subprocess execution, or multiplexer operations. A delete racing a pending creation waits for its scope/lifecycle ownership and cannot deregister it while publication is possible. Test races before/after registration commit, stage creation, owner-marker write, publication, split, and placement commit, as well as process death while each lock is held.

### Teardown, Rollback, and Recovery

Implement cleanup as a profile-scoped adapter. First fence and settle admitted active/queued turns and native managed background work, deliberately including persistent jobs; then invoke `hermes profile delete <owned-profile-name> --yes` with the recorded root and verified profile incarnation, established initially from the matching row/owner marker. Bind each cancellation target to durable owned session/task and PID/start witnesses. Pin the supported API sequence and verify its ordering against late producers and notifications: a retired authority may refuse later process-control requests, so capture-before-retire alone supplies no completion barrier. The complete native managed inventory and every individual cancellation outcome must reconcile with independently observed process settlement before final deletion. M4 proves this ordering while the shared gateway and unrelated profiles remain usable. Use only scoped control and verified owned targets; gateway-wide stop/restart, process-name killing, service installation and privileged escalation remain outside this adapter.

The installed Hermes deletion path can wait 60 seconds for profile ownership release. Preserve CAFleet's five-second *foreground command* deadline by running that mutation in a finite owned cleanup worker, rather than killing it every five seconds. This introduces one hidden implementation command, `cafleet internal hermes-cleanup MEMBER_ID OPERATION_ID`; it performs cleanup only for a preauthorized matching runtime row, has closed stdin and no service/daemon registration, and exits when that operation settles or reaches its own deadline. It never closes panes or deregisters members.

Under the lifecycle/scope/pane locks, the foreground stores `cleanup_queued`, a fresh operation ID, its `cleanup_action`, and a null result before spawning the worker. It releases the locks so the worker can acquire the exclusive scope lock. The worker has five seconds from launch to acquire it; on expiry it exits without mutation and leaves the queued row available for retry. Once acquired, it revalidates the token, member/runtime row and verified ownership before proceeding. A late worker with an obsolete token exits without effects. It acquires no fleet or pane lock and therefore cannot invert the common hierarchy.

Every transition below is a committed database write under the exclusive scope lock. A worker retains that lock from its token check through dispatch, observation and result settlement. Durable writes use the existing database completion-budget mechanism; a failed intent write prevents subprocess launch, and a failed result write leaves intent/uncertainty visible for recovery.

| State/transition | Exact ordering and permitted recovery |
|---|---|
| Owned published profile in `reserved`, `published`, `cleanup_required`, or eligible prior completion → `cleanup_queued` | Foreground chooses action/token and clears the previous result, commits, then spawns. A crash before spawn has queued state and no dispatch. |
| Queued row after foreground/worker crash | Acquiring the free scope lock while the row is still queued proves `not_started`: every worker must commit dispatch intent first. The foreground may replace the token and reschedule; an old delayed worker subsequently fails token validation. |
| `cleanup_queued` → `cleanup_dispatch_intent` | Worker verifies/records the directory incarnation and commits intent for the exact action before launching any destructive subprocess. A crash immediately before or after launch is conservatively ambiguous. |
| Intent → `cleanup_completed` | After subprocess exit, local process-group settlement and captured exit status, commit `cleanup_result` as JSON `{action, exit_code, group_reaped: true}`. A crash after exit but before this commit remains ambiguous intent. A success code alone does not establish gateway quiescence. |
| Intent with no remaining lock holder, or an unconfirmed child/gateway effect → `cleanup_uncertain` | Reconciliation records uncertainty; token replacement/destructive redispatch is prohibited until the prior operation is proven complete/quiescent through M4's observation contract. A free lock alone proves neither. |
| Completed/uncertain operation with proven quiescence → next queued action | A known failed partial delete may continue only against the recorded matching incarnation after prior completion. An identity-purge action gets its own queued/intent/completed cycle and operation ID. |
| Completed operation plus full profile/stage/identity settlement → `settled` | Commit final settlement before pane/registry finalization. A repeated delete skips Hermes mutation. |

Require `cleanup_action` and a nonempty operation token in every queued/intent/completed/uncertain state. Queued/intent states have a null result; `cleanup_completed` requires the valid result above; uncertain/settled states retain a valid prior result when one was committed. Retain verified incarnation evidence independently across these transitions and assert all row invariants when loading it. A second delete encountering the worker's scope lock observes/joins that operation rather than launching another. The foreground reserves its last second for durable-state read/reporting and returns success only after finalization; otherwise it exits 1 with `Hermes cleanup pending for member ID; operation OPERATION_ID; re-run cafleet member delete ID`. Pending and uncertain responses explicitly mean execution may still be running.

The worker has a 90-second monotonic budget after acquiring scope ownership. Its Hermes subprocess runs in a fresh process group with literal argv and captured redacted diagnostics. Keep the runtime lock's open-file description inherited by the local cleanup helper/subprocess, using safe descriptor APIs, so the creator/worker dying does not release ownership while a local destructive helper is alive. Reserve the last three seconds: send SIGTERM to the owned group, escalate to SIGKILL after one second, reap the direct child and verify the group is gone within another second, then persist the outcome with the final second. The foreground's process death does not cancel this already-authorized cleanup. The worker's cancellation/termination handler follows the same group settlement protocol.

If a child/group escapes or remains alive, or a gateway operation may continue after local termination, retain `cleanup_uncertain`; interpret stale dispatch intent the same way. The committed intent preserves that uncertainty even when a crash prevents the worker's final state write. A queued operation is the sole phase in which a free scope lock proves that dispatch never occurred.

`cafleet member delete ID` is also the reconciliation entry point. It first observes the recorded profile's tombstone/discovery state, the scope's native `gateway.lock` ownership, and the previous cleanup operation's completion. Acquiring the native maintenance reservation establishes that the gateway has released that profile only on builds where M4 proves it is the last writer-release barrier. An absent directory alone is insufficient. Accept `quiescent` only when the old operation has completed, the profile cannot be re-adopted, and no owned local helper/background writer remains. Accept `not_started` only when the operation never passed dispatch. A pending/unknown result returns the same recovery command and retains the row; it performs no mutation. The supported-build fixture must specify the exact read-only observation/control-completion mapping. If the selected build cannot supply that proof, M4 fails and the backend remains unreleased until a reviewed adapter/protocol change supplies it.

After a quiescent partial deletion, remove any remaining owned directory/stage and settle identity with `hermes profile purge-identity <profile-name>` under the same operation lock, only after the prior operation is confirmed complete. The inspected `profile_identity.py` treats that profile-specific action as idempotent and refuses a newly live profile. A nonzero/unknown result preserves `cleanup_uncertain`; it never triggers a shared-gateway restart. A normal successful profile-delete exit is accepted only with the same quiescence/absence checks. Record `settled` after profile, hidden stage and durable Hermes identity are all settled.

Member deletion therefore has two phases:

1. Acquire/revalidate lifecycle, scope and concrete pane locks; enforce the root-Director guard. Reconcile or authorize the single cleanup operation as above. Hidden-only `reserved` state can be cleaned synchronously because it was never discoverable.
2. Once the runtime row is `settled`, reacquire/revalidate the same locks, close any owned pane with normal layout handling, then deregister and remove the runtime row in one transaction. All profile/stage/marker files were removed before this commit. A pane-close or database failure retains the `settled` row so retry performs no Hermes mutation.

Creation rollback transfers the owned runtime to this same cleanup path before deregistration. Extend the registration guard so failed or pending cleanup retains an active pending member/runtime row. Report the original launch error first and the operation/recovery command afterwards. Apply this to preparation, substitution, split, uncertain split, placement-update and termination failures. A crash at any boundary is recovered with the same member-delete command; doctor reports the durable state read-only.
