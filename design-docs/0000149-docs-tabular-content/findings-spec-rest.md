# Findings: docs/spec (webui-api, coding-agent-backends, data-model, message-envelope, multiplexer-backends)

## Summary

18 tabulate-me findings and 1 table-misuse finding across the five files: `webui-api.md` 4, `coding-agent-backends.md` 5, `data-model.md` 1, `message-envelope.md` 2, `multiplexer-backends.md` 5, plus 1 cross-file finding (F5) whose restatements live in both `webui-api.md` and `data-model.md`. The dominant pattern is the **repeated per-item paragraph**: a page introduces N parallel subjects (three coding-agent backends, two multiplexer backends, seven schema tables, nine HTTP endpoints) and then re-states the same attribute for each one in its own prose section, so the reader must hold the axis in their head while scrolling. `coding-agent-backends.md` and `multiplexer-backends.md` are the worst offenders — the latter contains **zero tables** despite being a two-backend comparison page whose every section is a "**tmux** … / **herdr** …" bullet pair. `webui-api.md` restates the same two fleet-scoping errors (400 on `X-Fleet-Id`, 404 `Fleet not found`) in three separate endpoint sections. `data-model.md` is the healthiest — it already carries an ER diagram plus three well-formed tables — and needs only one summary matrix over its seven `###` table subsections. `message-envelope.md` has good tables that are incomplete rather than absent: its field table covers JSON rendering but not the text-mode rendering documented two sections below.

## Tabulate-me findings

### F1. docs/spec/webui-api.md — per-endpoint **Errors** blocks (`### GET /api/members/{member_id}/monitor`, `### PATCH /api/members/{member_id}/monitor`, `### POST /api/messages/send`) + `## Error Format` — status/error codes are prose and bullets, and the fleet-scoping rows are restated three times

- **Location**: `docs/spec/webui-api.md`, the `**Errors**:` blocks under `### GET /api/members/{member_id}/monitor — Member Monitor Config`, `### PATCH /api/members/{member_id}/monitor — Edit Member Monitor Config`, and `### POST /api/messages/send — Send Message`; plus `## Error Format`. *(This is the user's second named seed example.)*
- **Current form**: two prose paragraphs and one bullet list. GET: "**Errors**: 404 (`detail: "Member not enrolled"`) when the member is not in the…". PATCH: "**Errors**: 422 on an invalid body (e.g. `interval_seconds < 1`, wrong type) —…". POST: "- 422: Missing or invalid request-body fields (`from_member_id`, `to_member_id`, or `text`)…".
- **Proposed table columns**: two tables.
  - **(a) A shared fleet-scoping error table**, placed at the end of `## Request Headers`: `Status | detail | Trigger`. Rows: `400` (no `detail` string documented) — a missing or non-integer `X-Fleet-Id` header; `404` — `Fleet not found` — the header names a fleet id that does not exist. One sentence introduces it: these two apply to **every** fleet-scoped endpoint. The three per-endpoint blocks then drop their duplicate copies and the endpoint tables carry only endpoint-specific rows.
  - **(b) A per-endpoint `**Errors**` table** in each of the three sections: `Status | detail | Trigger`.
- **Row keys**:
  - GET `/api/members/{member_id}/monitor`: `404` / `Member not enrolled` / the member is not in the fleet, or is not enrolled (the monitoring member, deregistered, placementless).
  - PATCH `/api/members/{member_id}/monitor`: `422` / (FastAPI validation array, not a `detail` string) / an invalid body — e.g. `interval_seconds < 1`, wrong type; `404` / `Member not enrolled` / the member is not in the fleet or not enrolled.
  - POST `/api/messages/send`: `422` / (FastAPI validation array) / missing or invalid `from_member_id`, `to_member_id`, or `text`; `400` / (the page words this as the condition `from_member not in fleet`, not as a quoted `detail` value — keep that wording verbatim rather than promoting it into the `detail` column) / `from_member_id` is not an active member in the caller's fleet; `404` / `Member not found` / `to_member_id` does not resolve to an active member in the fleet (unknown, cross-fleet, or deregistered).
- **Prose that must remain**: all of `## Error Format` — that WebUI API errors use FastAPI's default error shape, the `{"detail": "Error message"}` code block, and the statement that 422 responses use FastAPI's default validation format (a `detail` array of per-field error objects) rather than a `detail` string. That last fact is why the 422 rows' `detail` cells cannot carry a quoted string and must point at this section. Also keep the POST section's cross-reference sentence pointing the 400 case at [Request Headers](#request-headers).
- **Why**: a reader debugging a 404 currently has to decide which of two `detail` strings they are looking at by reading two prose paragraphs; the table makes status → `detail` → cause a single row lookup, and hoisting the shared rows removes the triplication.
- **Priority**: High
